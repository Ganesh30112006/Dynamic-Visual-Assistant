Build a frontend for an **AI-powered real-time visual presentation assistant**.

The application is NOT intended to replace PowerPoint. It is a **lecture/presentation augmentation system** that listens to live speech, understands the current topic and presentation state, and displays relevant visual content when useful.

The frontend must be simple, professional, natural-looking, responsive, technically correct, and easy to use during a real lecture.

## 1. Technology requirements

Use exactly:

- React
- TypeScript
- TSX
- React Router
- Plain CSS / CSS modules
- No Tailwind CSS
- No unnecessary UI libraries
- Component-based architecture
- Clean separation of components, pages, hooks, services, types, and styles
- Use WebSocket-ready architecture for future real-time speech/context updates
- Do not implement IoT features
- Do not create unnecessary microservices in the frontend
- Do not hardcode fake AI behavior as if it were real

The project must run correctly with:

```bash
npm install
npm run dev
npm run build
```

No TypeScript errors, no broken imports, no missing routes, no console errors, and no placeholder functionality presented as completed functionality.

---

# 2. Main product concept

The lecturer first creates a session and enters the topics they intend to cover.

Example:

```text
Machine Learning

1. Introduction
2. Supervised Learning
3. Classification
4. Regression
5. Neural Networks
```

During the session:

```text
Microphone
   ↓
Live speech recognition
   ↓
Context understanding
   ↓
Presentation state
   ↓
Visual recommendation / visual display
```

The frontend must visualize this process clearly.

The frontend should support these presentation states:

```text
ACTIVE
FOCUS
EXAMPLE
DISCUSSION
Q_AND_A
MANUAL_LOCK
RESUME_PENDING
```

The lecturer must always be able to override the AI.

---

# 3. Overall UI philosophy

Do NOT make the interface look like a complicated enterprise dashboard.

Design it like a modern educational/professional application.

Use:

- generous spacing
- clear typography
- simple cards
- subtle borders
- restrained use of colors
- clear visual hierarchy
- minimal icons
- no excessive gradients
- no excessive animations
- no unnecessary charts
- no crowded sidebars

The primary screen should always focus on:

1. What topic is being discussed
2. What the system is currently doing
3. What visual is being shown
4. Whether AI visual assistance is active or paused
5. How the lecturer can override it

The UI must be understandable without documentation.

# 9. Focus mode

When the lecturer is explaining a topic deeply, the system should stop changing visuals while continuing to track speech/context.

The UI should clearly show:

```text
FOCUS MODE

Visual assistance is temporarily paused while context tracking continues.
```

Do NOT display "microphone paused".

Speech recognition must remain visually represented as active.

Important distinction:

```text
Speech Recognition = ACTIVE
Visual Switching = PAUSED
```

Do not incorrectly present these as the same thing.

Provide:

```text
Resume Visuals
```

and:

```text
Continue Automatically
```

if appropriate.

# 10. Resume pending state

When the system detects something such as:

```text
"For example..."
"Let's look at..."
"Consider this..."
"Now let's compare..."
```

the backend may send:

```text
RESUME_PENDING
```

The frontend should show:

```text
Possible transition detected

Resume visual assistance?

[Resume] [Stay Focused]
```

Do NOT automatically claim that the AI has correctly understood the lecturer.

The frontend should display the actual backend state.

# 20. Realtime architecture

Prepare the frontend for WebSocket events.

Create a dedicated service:

```text
src/services/realtime/
```

The frontend should be capable of receiving events such as:

```ts
type RealtimeEvent =
  | {
      type: "transcript";
      text: string;
    }
  | {
      type: "topic_update";
      topicId: string;
    }
  | {
      type: "state_update";
      state: PresentationState;
    }
  | {
      type: "visual_update";
      visual: Visual;
    }
  | {
      type: "connection_status";
      status: ConnectionStatus;
    }
  | {
      type: "resume_pending";
      reason: string;
    };
```

Do not place WebSocket logic directly inside UI components.

Use a custom hook such as:

```text
useRealtimeSession()
```

# 28. Important logical rules

The frontend must respect these rules:

1. Do not change the visual just because a keyword appears.
2. Do not automatically switch from FOCUS to ACTIVE without a backend-confirmed transition.
3. Do not confuse speech recognition status with visual assistance status.
4. Manual lock must override automatic visual switching.
5. Do not display fake AI confidence.
6. Do not mark topics complete unless the backend reports completion.
7. Do not fabricate transcript text.
8. Do not fabricate visual sources.
9. Do not lose the current visual during normal UI state updates.
10. Do not reset the session state when the component rerenders.
11. Handle WebSocket reconnection without destroying the current session state.
12. Prevent duplicate WebSocket connections.
13. Prevent race conditions between manual actions and incoming realtime events.
14. Never allow stale realtime events to overwrite newer state.
15. Validate all API data before rendering it.

---

# 29. Priority rules for UI state

Use this conceptual priority:

```text
MANUAL COMMAND
      ↓
MANUAL LOCK
      ↓
BACKEND PRESENTATION STATE
      ↓
BACKEND VISUAL UPDATE
      ↓
CONTEXT INFORMATION
```

The frontend should never independently invent a presentation state that conflicts with the backend state.

The frontend is responsible for **displaying and controlling the session**, not pretending to be the AI engine.
